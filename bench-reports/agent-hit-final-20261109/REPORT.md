# Agent 命中率定案：池容量是唯一根因，无第二损失源（2026-11-09，生产零改动）

> 承 agent-pool-20261109：衰减曲线定档后，本刀修观察路径、拿时序证据，
> **推翻了"第二损失源"假说**。生产仍零改动。

## 一、先平反：RADIX_DEBUG 仪器没有坏

dbg5 的"只打 2 条"不是仪器失灵——是 **agent_bench 客户端偶发卡死**
（本会话两次：进程活着、0 请求发出、timeout 后 exit≠0；服务端 health 一直 ok）。
正常跑完的会话 admit/match/retain 三点齐全。**教训：bench 卡死先看服务端 health
再怪仪器。**

## 二、时序证据（c=2×2，WEIN_RADIX_DEBUG）

```
admit seq=423/421 hit=0            ← turn 1 冷启 ✓
retain seq=509  full=31  snaps=2张  ← 树 31 块，持 2 张快照
match  seq=3050 blocks=26 tokens=416 ← turn 2 命中 = turn-1 prompt 末快照 ✓
```

机制正常：**每轮 prefill 末采新快照，下一轮命中它，逐轮滚动**。

## 三、c=4 的决定性异常 → 统一根因

c=4×6 每轮命中**恒 416**（不滚升），retain 显示 `cover=26`：
**树对本会话的覆盖只有公共系统 prompt 26 块**——各会话的私有链在互相驱逐
（LRU 下 4 条链轮转被逐，只保得住共享前缀）。

统一理论（推翻"第二损失源"）：

| 并发 | 全历史树需求 | 8K 池命中 | 32K 池命中 |
|---|---|---|---|
| c=1 | 13K | 71.7%（单链 LRU 只吃老块） | — |
| c=2 | 26K | 37.8% | **67.5%** |
| c=4 | 52K | 9.8% | **27.6%** |
| c=16 | **208K** | 10-20% | 15-27%（64K 池 16-22%） |

**c=16 命中的物理上限由显存决定**：208K token ≈ 13GB KV，24G 卡放不下
（权重 8.4 + 状态池 6.4 + 图/激活 + 快照 1.6 已 ~18GB）。vLLM 67.8% 靠
gpu-mem 自动大预算的同理。**不是 bug，是资源边界。**

## 四、可选后续（按性价比）

1. **驱逐策略**：LRU → 会话链保护（每活跃会话保护最近 K 块），同池提命中。
   纯调度侧，风险低，预期 c=4@8K 从 9.8% → 25%+。
2. **KV 压缩**（bf16→int8/fp8）：池容量 ×2，精度代价需 oracle 复验。
3. **文档化**：c≤2 建议 `--kv-pages 2048`（+30pt 命中）；c=16 说明物理边界。
