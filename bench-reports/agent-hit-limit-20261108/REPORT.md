> 本刀想再推一档，跑了四个实验，**全部被数据否证**，代码已回滚（HEAD 仍为 e5dc4c0）。

## 一、决定性对照：c=1 命中 71.7%，c=16 只有 41.6%

c=1×6 的 admit 时序（`WEIN_RADIX_DEBUG`）：

```
seq= 421 keep=  0  hit=   0        ← 首轮
seq=1785 keep= 26  hit= 416        ← 命中上一轮全部（421）
seq=3148 keep=111  hit=1776        ← 命中上一轮全部（1785）
seq=3193 keep=196  hit=3136
seq=3231 keep=199  hit=3184
seq=4584 keep=201  hit=3216
总命中率 0.7167
```

**理论最大命中率**（每轮都能复用上一轮全部前缀）：
`(0+421+1774+3148+3193+3231) / (421+1774+3148+3193+3231+4584) = 71.97%`

单会话实测 **71.67% = 理论值的 99.6%** ⇒ 命中机制（块匹配 + 快照恢复 + 末 token 重算）已无可改进。
c=16 的 41.6% 全部损失在并发。而上一刀的 c=16 里也有 `keep=201` 的完美案例 ⇒ 是**部分会话**退化。

## 二、四个实验，全部否证

| 假设 | 做法 | 结果 |
|---|---|---|
| 快照槽不够 | `--snap-slots 128`（显存 +1.6GB） | 命中 36.5/38.3/40.1% ⇒ **无改善**（vs 41.6%） |
| 页池不够，深层块被逐 | `--kv-pages 8192`（96K→128K token） | 36.5/40.8/32.4% ⇒ **无改善** |
| 末步不落块边界 | 分析 `fwd=4655`（%16=15） | 只差 15 token，且 15<16 时 `snap_align` 刻意不对齐（进度优先）⇒ **影响可忽略** |
| 共享快照被"采新还旧"提前还池 | 改成只解绑不还池 | 64 槽：22/16/8%（**反劣**，槽泄漏触发 radix 驱逐）；256 槽组合：39/17/10%、TTFT 26s（**显存吃穿**） |

第四条的机理值得记住：**"不还槽"必须配精确的回收策略**，否则泄漏的槽会让
`acquire_slot` 去驱逐 radix 块——那是拿 KV 换快照，净损失极大（第 3 发命中崩到 8%）。
这也解释了为什么 vLLM 的状态缓存与 KV 块是**一一绑定、随块引用计数释放**的。

## 三、真正的瓶颈（下一刀的方向）

我们的模型是「**请求私有槽 + 借还**」：`st.snaps` 记该请求持有的槽，采新时还旧。
并发下同一个前缀块被 16 个会话共享，但槽的归属是"某一个请求"——它退场/换新时，
共享块的命中点就消失，后来的会话只能退回浅层。

vLLM 的模型是「**状态缓存与 KV 块一一对应**」：块的引用计数归零才回收状态。
这在我们这里需要把 `snap_of_block`（块→槽）从"辅助索引"升级为**所有者**：
槽的寿命只由块决定，`st.snaps` 退化为只读引用，`acquire_slot` 只从"无块映射的槽"里分配。

这是结构改造（涉及 acquire/release/evict 三处），不是配置能解决的——本刀的四次否证
正好排除了所有便宜路径。
