# 池+准入联动扫参：全部劣于 512 页现状（2026-11-09，生产零改动）

> 前置结论（agent-hit-final）：命中差 = 缓存预算差（0.5GB vs vLLM ~10GB）。
> 本刀验证"池 2048 页 + mix_cap 调优"能否拿到正收益。**答案：不能。**

## 二、为什么命中 ×3 却 turns/s 减半

**混合步长尾主导**：mix_cap 512 档 ITL p50=12.8 但 **p95=47.5ms**——每次
prefill 段穿批时 decode 行被拖一整个 512-token 步。会话内串行链上这些慢步
累积，最后的会话被拖长（wall_s=11.9s 但 turns/s=2.18 ⇒ 会话交错长尾）。

命中 +18pt 省的 prefill（~0.3s/会话）< 长尾代价（~2s/会话）。

mix_cap 进退两难：调小（192）⇒ 3000-token turn 切 16 步、TTFT 崩（1.7s）；
调大（512）⇒ 每步更重、ITL p95 崩。384 命中还意外掉（快照格点与步界错位，
待查但已无关决策）。

## 三、vLLM 为什么行：正循环，不是单点技术

vLLM 67.8% 命中 ⇒ prefill 量小 3 倍 ⇒ 挤队轻 ⇒ 敢用大池 ⇒ 命中保持。
我们 11-30% 命中 ⇒ prefill 量 ⇒ 混合步长尾 ⇒ 大池负收益。**进不去这个
循环的物理原因：13GB 需求在 24G 卡上装不下**（权重 8.4 + 运行态 6.4 +
图/激活 + 快照 1.6）。

## 四、决策

1. **生产保持 512 页 + mix_cap 192**，Agent 命中线收官。
2. 剩余路径只有"改变成本结构"的刀：快照瘦身（25.2MB/张 → deltanet-only
   或 int8，槽 64→128+）、KV int8（池 ×2）。它们把"装得下的历史"翻倍，
   才可能进入 vLLM 的正循环。
3. c=2 场景文档化建议 2048 页（命中 37.8→67.5%，无挤队）。
