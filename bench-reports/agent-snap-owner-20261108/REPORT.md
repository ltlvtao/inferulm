# 快照槽随块走：Agent 命中 30% → 41.6%（2026-11-08）

## 一、vLLM 热态口径校准（本刀先做，因为上一轮对比表口径偏乐观）

清前缀缓存（`POST /reset_prefix_cache`，需 `VLLM_SERVER_DEV_MODE=1`）+ 三发取中位：

| 组 | vLLM turns/s | 热 TTFT | ITL p50 | 命中 |
|---|---|---|---|---|
| c=4×6 | 2.20 | 138ms | 12.06ms | 67.3% |
| c=8×6 | 3.62 | 142ms | 13.06ms | 67.0% |
| **c=16×6** | **5.50** | **203ms** | **14.91ms** | **67.8%** |
| c=32×6 | 7.08 | 260ms | 19.60ms | 67.7% |

与历史读数（5.72 / 15.0 / 70.7%）同档 ⇒ 口径没漂。**vLLM 的命中率在四档都稳定在 67-68%**，
说明"必然重算的新增消息"上限远高于我们上一轮估计的 68%——它的块级状态缓存几乎吃满。

一处配置纠错：`--tool-call-parser qwen3_engine` 不是合法名（那是模块文件名），
枚举里是 `qwen3_coder|qwen3_json|qwen3_xml`；模板输出 XML 形态 ⇒ 取 `qwen3_xml`。

## 二、真因：`retain` 把"树已覆盖段"的快照全还池了

debug 日志（c=4×5）里矛盾很硬：

```
retain seq=4656 fwd=4655 full=290 shared=26 cover=198 snaps=[(990,23),(1007,25)]
admit  seq=4588 keep_blocks=26 hit_tokens=416
```

树已覆盖到 198 块（`cover=198`，因为 mock 工具结果逐字相同 ⇒ 路径高度重合），
但**浅层只 shared=26**。原因在退场路径：

```rust
for &(b, slot) in &st.snaps {
    if kept.contains(&b) { insert } else { snap_free.push(slot) }   // ← 旧
}
```

`kept` 只含"本次新插入段 `blocks[d..full]`"。落在树已覆盖段 `[0..d]` 里的快照
（深度 26..198 之间，正好是 agent 每轮最需要的那批）**每轮都被无谓还池** ⇒
下一轮只能命中浅层 26 块（416 token）。

改成**槽与块同命**：只要块索引 `< full`（块还活着——要么在树覆盖段、要么进新段），
槽就保留；块被逐出时由 `snap_owner` 回收（上一刀已建）。

## 三、读数（c=16×6，每发前清前缀，三发）

| | turns/s | 热 TTFT | ITL p50 | 命中 |
|---|---|---|---|---|
| 门槛 64（上一刀） | 2.45 / 2.25 / 1.90 | 2287 / 3527 / 4577 | 37.65 / 37.41 / 40.57 | 30.5 / 30.5 / 20.3% |
| **槽随块（本刀）** | 2.24 / 2.95 / 2.61 | 3014 / **1283** / 1865 | 39.11 / 37.39 / 38.24 | 33.8 / **45.5** / 41.6% |

**命中 +11.6pp（30 → 41.6% 中位）、TTFT −47%（3527 → 1865ms）、turns/s +16%**，ITL 不变。

满载 battery 无退化：图档 **4321.1 tps @ 20.85ms**（上一刀 4323.8 @ 20.86），轻载 11.79。

## 四、回归

`wein-exec`：8 + 1 + 3 + **23** + 2 + 3 全绿；`qg3`（图档步时延 < eager）在全量并行下曾红一次，
单跑绿 ⇒ 既有 flaky（单请求 decode 步时延，与本次改动的退场路径无关）。

## 五、剩余差距拆解（41.6% vs 67.8%）

1. **快照点对齐**：`fwd=4655`（%16=15）意味着 prompt 末步不落块边界 ⇒ 端点那张采不到，
   深点只能到 4096。调度侧 `snap_align` 只在"chunk 吃满 backlog"时圆整，
   agent 的 span（190/559）路径上常不触发。
2. **槽预算**：每请求 2 相位 × 16 会话 = 32 < 64 槽，已经不缺；但浅层共享 + 深层混用同一池，
   长会话（>8 轮）仍可能互相挤。
3. **ITL 38ms vs vLLM 15ms**：与命中无关的部分——prefill 配额与 decode 争 GPU（`mix_cap` 192）。
