# 满载 skinny-m 自写 GEMM：负结果判决（2026-11-07）

> 上一刀（`f65bd8f`）把满载真账定位到 gemm：权重字节恒定 8.41GB/步，带宽随 m 塌陷
> 1022 → 712 GB/s（m=1 GEMV 贴天花板，m≥32 交 cuBLASLt 掉 30%），满载差 vLLM 的 3.3ms
> 全在这里。本刀按计划自写 skinny-m GEMM 试图接管 m∈[16,128]。
>
> **判决：打不过 cuBLASLt，默认关，代码留库作负结果与后续 split-K 实验的底座。**

## 0 结论

| 指标 | 自写 `gemm_skinny` | cuBLASLt | 差 |
|---|---|---|---|
| in-stream gemm 段（m=100，160 发/步） | **23.36 / 23.37 ms** | 11.67 / 11.76 ms | **2.0× 慢** |
| 有效带宽（含 A 复读流量） | 989 GB/s | 721 GB/s | 我们高 37% |
| 每步总字节 | 23.1 GB（2.75×W） | 8.41 GB（1.00×W） | — |

**根因是流量的代数，不是流水线深度也不是占用率**：块=64 列 n 片时权重必须每块各读一遍
（否则权重被重读 n/64 次），对称地 A 片也必须每块各读一遍 ⇒ A 流量 = `(rows16/64)×权重`
（m=100 ⇒ rows16=112 ⇒ **1.75×W**）。我们已经把每字节搬到 989GB/s（D2D 标定 848-920，含部分
L2 命中），但要赢 cuBLASLt 需总流量 ≤ `920/721 = 1.27×W` —— 任何"填满 128 SM"的切法都做不到
（§5 的三种切法全算过）。

## 1 设计与实现

- 几何：块 = 一个 64 列 n 片，`grid = n/64`（n=8192 ⇒ 128 块 = 128 SM 一波填满）。
  bdim = 128（m≤64）/ 256（m>64）；8 warp = n 子片 `w&3` × m-tile 组 `w>>2`，每 warp 至多
  4 个 16×16 C 片段（`acc = [[f32;8];4]`）。
- W slab `[64][KC]` 与 A slab `[128][KC]` 走 `cp.async.cg` 16B 进 smem（`SK_LD = KC+8` u16 =
  +4 bank 偏移、16B 对齐），`wmma.m16n16k16` bf16→f32 累加。
- 写回：每 warp 一段 256 f32 舞台 `SK_O`，`wmma_store_c` → `f32_to_bf16` → `C[m][n]` 行主序。
- 资源（KC=64 单槽）：**64 regs / 0 spill / 35840B smem / 1 barrier**。
- 数值合同：mma 的 k 累加序与 cuBLASLt 不同 ⇒ 只能容差档（o43 实测 rel2 2.54-3.49e-6，
  峰值归一 ≤1.43e-3，门 3e-3）；另留一条 `run_wt` 恒等锚（W=I、n 非 64 整倍 ⇒ 默认路逐位等于 A）。

## 2 三个真 bug（都由 o43 / in-stream 抓出）

1. **B 片段列偏移**：`nsub * SK_LD` 应为 `nsub * 16 * SK_LD`（16 列子片前进 16 行）。
   症状：第 16 列之后整片错（o43 `33×192×96` 元素 16 got 243 vs ref 176.5）。
2. **末片 cp.async 竞态**：`cp.async.wait_group 1` 允许**最新**一组仍在飞，而末片自己就是最新
   一组（其后不再补片）⇒ 读到未落盘 smem。症状：`128×8192×2560` 元素 586 偶发超容差
   （33/16/64/100 四档全过，只有最后一块 m-tile 组满编时暴露）。改末轮 `wait_all`。
3. **单槽版写回越界**：写回暂存沿用 `SK_W[0] + warp*256 f32`（8 warp × 256 f32 = 8KB），
   而单槽 `SK_W` 只有 5120B ⇒ `cuStreamSynchronize: CuError { code: 700, "an illegal memory
   access" }`。独立出 `SK_O`（8KB）修掉。
4. 宿主/内核常量耦合：`SKINNY_KC` 必须与 kernel 的 `SK_KC` 同步（改 64 若只改一侧，k 尾
   会被静默截断）。kernel 不处理 k 尾 ⇒ 宿主门 `k % 64 == 0` 是唯一防线。

## 3 三档配置实测（in-stream gemm 段，`WEIN_STEP_PROFILE=1 qwen_step_profile 100`）

| 配置 | gemm 段 (ms) | 说明 |
|---|---|---|
| KC=32 / 单槽同步 | 29.73 | 80 次 chunk 往返 + 2 屏障/片 |
| KC=32 / 三级 cp.async（wait_group 1，3 槽 46080B） | 25.01 | 片数不减，流水反劣 |
| **KC=64 / 单槽同步（本版）** | **23.36 / 23.37** | 40 次往返，35840B smem |
| cuBLASLt（默认路） | 11.67 / 11.76 | 721 GB/s |

小 m 不受影响（m<16 不接管）：m=1 8.21/8.34、m=8 9.85/9.81（on/off），差在噪声内。

## 4 旁证：为什么 m=1 能跑 1022GB/s 而 m≥16 不行

m=1 的 warp-per-row GEMV 没有 A 复读问题：A 只有 1 行（5KB），全块共读、L1 命中；且块数
2048 远超 SM 数。m≥16 时 A 变成 `rows16×k`（m=100/k=2560 ⇒ 573KB），任何"块内覆盖全 m"
的块都得搬 `rows16×k` 字节 —— 而"块内覆盖全 m"是权重只读一遍的必要条件。两条要求互相
夹死，这就是代数。

## 5 为什么封路（三种切法都算过，n=8192/m=100/W=41.9MB 单形状口径）

| 切法 | 块数 | A 流量 | C 偏和 | 合计 | 判定 |
|---|---|---|---|---|---|
| 64 列（本版） | 128 | 1.75×W | — | 2.75×W | 实测 23.4ms |
| 128 列 | 64（半 SM） | 0.875×W | — | 1.875×W | 实测 31.6 / 64.5ms（更差） |
| 256 列 + split-K 4 | 128 | 0.44×W | 0.63×W(f32 往返) | 2.06×W | 估算仍 ≥1.8×W |
| 16 行/块（m 摊开） | ×7 | W 重读 7 遍 | — | 7×W | 直接排除 |

要赢需 ≤1.27×W。宽到 400 列以上才可能，那时 n=8192 只剩 20 块（SM 半空）。
⇒ **cuBLASLt 的 721GB/s 之所以赢，是它不需要填满 SM 就能吃到这个带宽，而我们的结构必须先填满 SM。**

## 6 测量纪律（本轮新增）

- **单形状孤立探针不可信**：同一形状反复发 ⇒ 权重驻 L2（72MB），探针能测出 1114GB/s > HBM 上限。
  实例：`gemm_skinny` 838ms 单发在探针里 69.5µs（604GB/s，"看起来"只慢 cuBLASLt 2×），
  在真实流里 23.4ms/步。**判据一律用 in-stream 段表。**
- 诊断实验反例：把 A 片钳到"只读第 0 行"验证流量假设 ⇒ 反而 50.53ms（同地址 `cp.async` 退化），
  这类钳位实验不能用来判流量。
- `ncu` 本机无权限（`ERR_NVGPUCTRPERM`），DRAM 计数器不可用 ⇒ 只能用"代数 + 时间"反推流量。
