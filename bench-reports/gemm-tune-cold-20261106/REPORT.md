# gemm autotune 选型偏差：查清了，但只值 3–4%（否决，回滚）

## 0. 结论先说
- **假设成立**：现有 autotune 用"L2 热态 + 前 4 候选 + ws0 偏好"选 algo，确实**不是冷态最优**——3/8 形状
  warm/cold argmin 不一致，其中 `2560×4096`(out) 与 `2560×9216`(down) 的**冷态真赢家落在旧候选集之外**，
  全 #0 → 冷最优合计 **−3.7%**（流水态交错 **−3.6%**，34 层折算 703 → 737 GB/s）。
- **但端到端拿不到**：按冷态重写 `pick_algo`（全 8 候选 + 每发前 L2 读扫 + 中位）后，
  `qwen_step_profile` 的 gemm 段 **11.54–11.75 → 12.06–12.30（N=60 稳态）**，反而更差；
  满载 A/B 只 **+0.5~0.8%**（<3% 门禁）；prefill 无差、6009 冷 +1%。
- **处置：回滚**（`cublaslt.rs` 复原到 HEAD），保留探针 `examples/gemm_cold_probe.rs` 作证据。
- **判定：m=100 形状的 cuBLASLt 已到极限。668→800 GB/s 这条路上没有 algo 选择的钱。**

## 1. 为什么不是"选错了算法"：逐候选冷/热实测
探针 `gemm_cold_probe`（m=100，wt=true，全部 returned 候选，7 轮中位；L2 读扫 = 128MB/155.6µs = 862 GB/s）：

大形状里没有一个是 900。

## 2. 为什么改了反而更慢（两条独立原因）
1. **调优债落在计量窗内**：全候选 × 3 轮 + 读扫 ≈ **20ms/进程**。20 步窗里每步只赚 ~1.5ms ⇒ 前 13 步白干。
   阶梯实验（ncand 1→8 × flush on/off 的 2×2）：`ncand≥5 才恶化`、`flush 恒 +0.28ms`。
   `WEIN_LT_PROTO=warm`+全 #0 = 11.54 vs **cold+全 #0 = 13.77** ⇒ **恶化来自调优过程，不是选型本身**。
2. **稳态也没赢**：N=20/40/60 拟合 warm 11.74/11.66/11.48、cold 13.74/12.43/12.06 ⇒ 每进程固定 +19.8ms、
   稳态每步 −1.5ms（约 100 步回本），但 N=60 时 cold 仍比 warm 差。原因：**真实流水里 8GB/步的 L2 驻留态
   与"单形状隔离测冷"不同**；新选型偏向 `ws==0` 的小 tile 族，在孤立冷态更快，在 8GB 交替流里反而更差。

## 3. 证伪清单（别再试）
- **"改 tuner 能把 gemm 段从 11.98 拉下来"** —— 端到端不成立（见上）。
- **"恶化来自 driver 上下文粘滞态"** —— `cuCtxGetLimit`/`GetCacheConfig`/`GetSharedMemConfig` 调优前后逐字相同；
  `cuCtxResetPersistingL2Cache`/`SetLimit`/`SetCacheConfig` 无改善。
- **"128MB 常驻稀释缓冲 / 多驻 module 是主因"** —— 只占 ~0.15/+0.34ms 每步；全关后 cold 仍比 warm 差 1.9ms@20 步。
- **"m=100 的大形状能到 900 GB/s"** —— 冷态逐候选上限：lm_head 888.8、down 820、gate/up 793、qkv 783、o/z 751、out 726。
  我们流水态实测 ~660 GB/s ⇒ **达成率已达冷态上限的 89%**，余下 11% 是 L2 抖动 + kernel 交叠，不是选型。

## 4. 顺带发现（下一步各自值 1–2%，本刀不做）
- `gate/up` 冷最优 #3 被**数值闸**拦（与锚差 1.15× 容差，低精度 split-K 族）——要拿这 3.3% 得单独审这条容差带；
- `lm_head` 冷最优 #1 快 3.8% 但没过 5% 滞回门——单形状放宽门禁值 3.8%。
