# 组织形态刀 B：小 N 投影的组织（消融值 0.40ms，合并只兑现 0.13ms ⇒ 回退）

## 0. 结论
- **判据通过**：消融（把对应 gemm 换成 no-op）证明 `32×2560`(a/b，48 发) 在**生产图档**里值 **−0.222ms/步**、
  `1024×2560`(full 层 k/v，16 发) 值 **−0.182ms/步**，合计 **−0.40ms/步（2.0%）**，两者每发真实占用 4.6–6.6 / 11.4 µs。
- **但合并拿不到**：`w_a‖w_b` 打成 `[64,2560]` 一发（方案 a，已实现并测）只 **−0.12~0.16ms/步（0.6%）**，< 1.5% ⇒ **回退**。
  原因：**n=64 的一发并不比 n=32 便宜**（微基准 n=32 → 10.90/20.08/10.68µs，n=64 → 15.93/17.82/10.85µs；
  cuBLASLt 改选 28 tile 宽 + 不同 split-K 段数），合并只是把「两发」的第二个固定开销换成更宽的 tile。
- **方案 c（q+k+v 合成 5120）天花板就是 kv 消融的 0.9%**，< 1.5% 阈值；**方案 b（a/b 挂进 8192 的 qkv gemm）**
  要牵动 conv_dim / 行 stride / `dn_split_qkv` / conv 状态池布局，风险与收益不对等 ⇒ 不做。
- **判定：gemm 的「发射开销」这条路走完，总计只值 2%，且实际可兑现 0.6%。**

## 2. 为什么 1.3–1.5ms 的「固定开销上限」只兑现 2%
表里其余形状（gate+up 66.6 / down 63.5 / qkv 59.4 / q/o 30.7µs）的「实测 − 纯带宽」不是发射开销，
而是**大 gemm 内部的 tile/occupancy 损耗**：对应 706 / 740 / 707 / 684 GB/s，已达 900 上限的 75–82%，
删不掉任何一发，只能**换 kernel**。所以"组织"能给的就只有 a/b + k/v 这 0.40ms。

| 32 | 10.90 / 20.08 / 10.68 |

**同形状跨进程算法 churn 让绝对值在 10.7–20.1µs 间跳**（这也是 eager 路径 ids 哈希不稳的同一根源）⇒
本机任何 <1ms 的 gemm 结论都必须同进程/多轮交错下判。
