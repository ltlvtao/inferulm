# pinned 暂存证伪 + 步时账的真正缺口（2026-11-06，HEAD 前 = bfc5a69）

对象：`svc-host-20261106` 判定的唯一可兑现项（pinned 暂存，预估 0.1ms/步 = 0.45%）。

## 一、做法（完整实现，已回滚，设计留档）

1. `cuMemHostAlloc(PORTABLE)` + `cuMemFreeHost` 绑定；线程本地**双层 ping-pong
   竞技场**（上传 128KB×2、回读 64KB×2），`pin_reset()` 在每步入口翻层。
2. `upload_on`/`upload_prefix_on`：pageable 源先抄进本层暂存（纳秒级），再发
   `cuMemcpyHtoDAsync`；竞技场用尽/捕获区间内**降级**回原路（绝不环绕——环绕会
   让排队中的拷贝被后续写踩掉）。
3. `read_to_vec`：pinned 目的（同步 D2H 直达 DMA）。
4. **抢先 D2H**（新）：`copy_out_pinned` 把采样回读**排进流**（与图尾 argmax
   保序），`sync` 一并等它，sync 之后只做主机侧拷贝。
5. `WEIN_PIN=0` 关闭快路（A/B 用）。

## 二、相位级确实生效

```
改前  [graph] 上传 63.6 + launch 512.3 + sync 19877 + 回读 55.6 = 20508（非 GPU 631.4）
改后  [graph] 上传 69.0 + launch 481.2 + sync 19925 + 回读  2.1 = 20477（非 GPU 552.4）
```

**回读 55.6 → 2.1µs**（那发同步 D2H 藏进了 GPU 计算里），宿主总量 −79µs/步
（−12.5%）。上传只降 0 到 −10µs：WSL 下每次拷贝 API 的固定代价 ~9µs，
pageable→pinned 省的只是暂存那一段。

## 四、为什么白干：步时账里有个 2.5ms 的洞（**本刀最有价值的发现**）

```
实测平均步时 = 22980 µs（4351.5 tps、1280 步）
exec 相位和 = 20477 µs（上传+launch+sync+回读）
                       ↑ 差 2503 µs/步 = 步时账的 11%，不在 exec 里
引擎 [loop] 前进/规划 = 190 µs
```

⇒ 剩下 ~2.3ms/步 既不在 exec 的宿主段、也不在引擎循环，只可能在**请求流转与
混合批**：`n=4000` 时每步都在"送走完工请求 + 收进新请求 + 新请求 prefill 行"，
那些步走不了纯 decode 桶图（`pure_decode` 护栏把混批挡到 eager/尾段路径），
单价远高于 20.5ms。

这也解释了上一刀为什么能值 +6.5%：`d6b5a0a` 砍的 95 发 memset 在**流转点**
（每步 1-1.5 次），正好落在洞的入口，而不是稳态 exec 里。

**宿主微优化在这一层没有杠杆**——0.55ms 全在 exec 内、已是最小；想动的是
那 2.3ms 的组织形态。

## 五、下一刀（建议）：把 2.3ms/步 拆开

给步循环加"路径分类 + 行数 + 步时"三列计时（一条 env 门控），按
`纯 decode 图回放 / 混批尾段 / 全 eager / 空步` 分类直方图，先定案这 2.3ms
有多少是 (a) 混批步的单价差、(b) 流转点固定开销、(c) 行数不足 100 的欠铺。
然后再决定：混批小 prefill 上桶图（清单第 4 项）、还是把流转点做得更薄。
