# 步时分类直方图：那 2.5ms「洞」是我算错的（2026-11-07，HEAD 前 = 8c20c3c）

对象：`pin-neg-20261106` 提出的"步时账差 2.5ms/步（11%）"，即"exec 相位之外
还有 2.5ms 不知去向"。结论先说：**没有这个洞**。上一轮的差是我把"每步 100 行"
当恒等式算出来的算术错误——真实平均 **96.6 行/步**（波次切换期批不满），
步时账是闭合的。

## 一、新仪器 `WEIN_STEP_HIST=1`

`wein-engine/src/core.rs` 步循环按**步形态**分类累计 `[步数, 墙钟, exec.step,
prefill token, decode 行]`，每 200 步印一组：

```
[hist] 纯decode    134 步 墙钟 2731.5ms(63.4%) 步均  20.38 其中 exec  20.16 引擎  0.23 | pf/tok     0 dec行  99.5
[hist] 混批          66 步 墙钟 1578.8ms(36.6%) 步均  23.92 其中 exec  23.58 引擎  0.34 | pf/tok   100 dec行  91.9
[hist] 合计  21.55ms/步（200 步）
```

（n=4000 / max_tokens=32 / c=100 / 图档，4483.7 tps；三次窗口完全一致，
纯 prefill 步与空步为 0 步。）

## 二、账闭合

```
实测：28.55s / 1325 步 = 21.55ms/步，平均 96.6 行/步（128000 token）
     [hist] 合计      21.55
     ├ exec.step      21.25
     ├ 引擎(前进+分发) 0.24
     └ 残差           0.06
```

上一轮的 22.98ms 来自 `100 行/步` 这个假设（`100 / (tps/1000)`）——真实行数
96.6，同一份日志按 21.55ms/步重算即 29.42s，与 wall 一致。**没有额外 2.5ms，
也没有"隐藏的流转开销"**。

## 三、混批步贵在哪：prefill 的真计算，且已在平价

- 混批步占 **33% 的步 / 36.6% 的墙钟**，步均 **23.92ms**（vs 纯 decode 20.38）。
- 它比纯 decode 多 3.76ms，但 decode 行少 7.6 行（≈ −1.54ms，按 0.203ms/行）
  ⇒ **100 个 prefill token 净成本 ≈ 5.3ms = 53µs/token**。
- 对照 vLLM 同口径：prefill 19.2-21.1k tok/s（3k 上下文）= **47-52µs/token**；
  我们长上下文 6009 冷 424ms/6009 token = **70µs/token**（更长的上下文、更贵的
  注意力）。⇒ 短上下文的混批 prefill 我们**已在同一量级**，不是浪费。
- `mix_cap=192` 正是把混批步钉在"92 decode + 100 prefill"这个形状上；
  历史扫描（192 vs 224，`bench-reports` 归档）tps 只差 +0.16% 而 p99 从 38.5
  涨到 44.2 ⇒ 往混批步里多塞 prefill **不划算**（总 prefill 计算量不变，
  只改变每步的形状）。

## 四、由此得到的判断

1. **吞吐剩下的杠杆只剩纯 decode 步的 GPU 工作**——那是 67% 的步 × 20.2ms，
   每砍 0.5ms ≈ +1.6% tps。vLLM 同口径下我们的差距项就是 norm/eltw 家族
   0.53ms/步（2.6%），需要破位级合同（`norm` 归约树形态）。
2. 混批侧若要再压，方向不是"塞更多"，而是**小 span 的 delta 单价**：
   `<256` token 的 span 走非 chunked 路径（32 块、SM 欠铺），而 ≥256 走
   chunked。可测实验：把 chunked 阈值 256 降到 128，看混批步 23.92 → ?
3. 引擎侧 0.24ms/步（1.1%）不再是目标。
